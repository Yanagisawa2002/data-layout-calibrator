## 2. 最小完整任务与最终输出

选定 [SimplePH b4d7512](https://github.com/rostanda/SimplePH/tree/b4d7512ed06873ac188b20ebf1639f1c4cf83afc)
的 `python/run_poiseuille_flow.py`：给定分辨率、Reynolds 数与步数，生成通道内流体及
边界粒子，执行实际的 `Solver::run`。每步包含 Verlet 第一阶段、cell grid/邻居维护、
密度、压力、边界条件、力及 Verlet 第二阶段。原应用定期写 VTU，供
`python/plot_poiseuille_flow.py` 与 ParaView 消费。

目前草稿的连通路径是：

1. 共用原生 C++ 主机产生 CPU 上的 canonical AoS 输入。
2. 选择的存储接收全部字段，承担分配和转换，持续更新同一粒子集合及邻居索引。
3. 按固定相位和频率写出全部 VTU 字段与拓扑；消费者读实际文件，生成速度剖面 CSV。
4. C# 主机调用 package 内新增的 `WholeTaskLayoutSelector.Select`，仅用校准数据冻结推荐。
5. 新的独立输入上单独启动 `selected` 策略进程，再调用 `Confirm`；固定策略的观测另行保留。

这是**新增实验性完整任务 API**，不是原有 component-P95 `LayoutSelector` 已经获得了
新实测收益。Unity NativeArray 生成存储、Burst kernels、Player 和部署 resolver 均不在
这条原生路径的验收范围。这里没有 GPU 数据、上传或回读。

### 边界需要先修订的一项问题

`simpleph_task.cpp` 当前把 `input.bin`、`state.bin` 高精度校验文件的写入放进主计时，
还增加了终态 VTU；上游原应用只按 `vtk_freq` 在步前导出。校验文件不是已有调用方的
消费需求，可能放大短寿命任务开销。**建议把全精度校验输出放到独立正确性模式，主指标
保留实际要求的 VTU 与速度剖面消费。** 若保留终态 VTU，应在任务契约中明确这是为了
交付有限调用的最终结果，并在所有方案统一计费。不能将当前适配称为未改变的上游 CLI。

主指标还应明确：开始于调用方发起任务，包含当前架构的原生子进程启动、输入生成、
拥有的存储分配/转换，止于全部要求的 VTU/剖面结果可供调用方读取并释放拥有的存储。
文件写入到 OS 缓存完成，未承诺持久化介质 flush。独立正确性校验与实验观测工具的
成本另记；选择策略总成本必须另加实际校准与决策主机时间，不能扣掉它实际依赖的
进程启动或控制成本。若以后采用常驻主机，须另行实测，不能用模型替代当前调用成本。

### 对照与冻结建议

| 对照 | 作用与公平条件 |
| --- | --- |
| 原始 AoS 应用路径 | 保留原邻居缓冲区生命周期，另报公共初始化/错误处理适配。 |
| tuned AoS | 复用邻居及 per-thread cell 缓冲区；这是合理固定基线。该改进的收益单独报告。 |
| field-SoA / field-AoSoA8 | 使用相同缓冲区复用、算法、双精度、邻居次序和线程预算，与 tuned AoS 比布局。 |
| 实际 LLAMA 布局 | 用 pinned `allocView` 与 SoA/AoSoA 映射；不是旧 code_comp 的手写数组替身。 |
| selected 策略 | 校准冻结后按推荐额外执行独立输入；不得以确认组最快者替代。 |

这些存储保留上游二维 `std::array<double,2>` 为叶字段，应准确称为 **field-SoA / field-AoSoA**，
不能说每个标量分量都已拆开。全部方案使用相同编译器、精度开关、OpenMP 单线程设置和
资源约束；线程扩展另作研究。

建议先压缩为五种有明确对应关系的场景，具体步数在**独立发现阶段之后、确认之前**冻结：

| 场景 | 建议校准 / 独立分辨率 | 需要回答的问题 |
| --- | --- | --- |
| 小规模短调用 | 12 / 13 | 输入、转换与结果交付是否已主导成本？ |
| 中规模多步、正常导出 | 24 / 25 | 多个真实处理步骤能否摊薄布局准备？ |
| 大规模多步、正常导出 | 48 / 49 | 工作集扩大时布局效果是否持续？ |
| 同一中规模寿命、每步导出 | 24 / 25 | 高频 VTU 与消费成本是否抵消收益？ |
| 同一大规模、短调用 | 48 / 49 | 同规模数据短寿命是否回退到固定布局？ |

上述粒子数分别是校准 240/768/2688、独立 273/825/2793；每种新分辨率包含非整块尾部。
独立输入还应采用未用于调参的 Reynolds 数和确定的位置平移。它们是新的通道输入，
不是把同一次内层迭代改名为独立样本。规模不宜无依据扩大到百万粒子。

必须完成的门槛：

1. 与原始路径逐字段比较完整高精度状态、所有要求的 VTU 字段/拓扑和实际消费结果；
   检查质量/type、optional engagement、有限数值、周期边界、尾块和错误导出。
2. 一条足够长的公开 Poiseuille 用例校验速度剖面/物理稳定性。只与同一算法输出相等

3. 先独立诊断原路径与 tuned AoS 的邻居维护/密度/压力/边界/力/积分/导出成本，再冻结。

5. 预注册整个 cohort 的负载、throttling 与固定基线漂移失败规则。保留失败组，

6. 报告固定 AoS、固定 SoA、实际 selected 与外部布局的完整任务值，再报告

Docker、RTX 5090 32607 MiB、驱动 580.76.05；cgroup CPU 额度为 25 核时间，cpuset
0–207；内存上限 90 GiB；系统盘 30 GiB、数据盘 50 GiB；PATH 中有 GCC 11.4 / CMake
3.22.1，未发现 dotnet/dxc/nvcc/Unity。未在 PATH 发现不等于确定未安装。

**25 核时间额度不是 208 个独占核；GPU 空闲也不证明 CPU、内存带宽或磁盘独占。**
原生单线程任务可以落在该 CPU 额度内，但仍需确认 CPU 型号、调度/NUMA、throttling、
共享负载和实际剩余空间。仅凭 RTX 5090 型号不能判断本任务是否比本机更合适。
